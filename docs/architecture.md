# dailyOS Architecture

이 문서는 2026-09-05 기준 dailyOS의 현재 구조와 앞으로의 변경 기준을 정리한다.

## 제품 구조

dailyOS는 모바일 우선의 개인 Life Database OS다. 현재 구현은 다음 흐름으로 읽는 것이 가장 정확하다.

1. **입력 계층**
   - 활동, 할 일, 이벤트, 기록, 건강, 사진, 수입 입력
   - 모바일 경로: `/m/record`
2. **조회·복원 계층**
   - 하루 타임라인과 상세 패널
   - 키워드 검색과 자연어 검색
   - 모바일 경로: `/m/day`, `/m/search`
3. **보조 관리 계층**
   - 사람, 가계부, 지도, 사진 묶음 조회
   - 설정, 백업, 데이터 삭제
   - 모바일 경로: `/m/other`, `/m/settings`

루트 `/`는 현재 `/m/day`로 리다이렉트한다.

## 현재 정보 구조

### 기록 입력

- 활동: 실제로 한 행동
- 할 일·이벤트: 계획과 약속
- 하루기록: 짧은 텍스트 맥락
- 건강: 몸무게와 러닝
- 사진: 날짜, 메타데이터, 연결 대상
- 수입: 날짜 기반 수입 기록

### 조회·해석

- 하루: 날짜 기준 통합 복원
- 검색: 전체 기록의 키워드 검색
- 자연어 검색: 질문형 조회와 요약 응답
- 사람: 함께한 사람을 축으로 한 조회
- 장소: 방문 장소와 저장 장소를 분리해 관리
- 가계부: 일정·활동·이벤트에서 파생된 수입/지출 흐름

### 보조 관리

- 설정: 계정, 알림, 데이터 관리
- 백업: Supabase 테이블을 JSON으로 내보내고 다시 가져오기
- 삭제: 현재 계정의 앱 데이터와 사진 스토리지를 함께 정리

## 데이터 연결 원칙

- 일정·할 일·이벤트는 계획과 약속의 축이다.
- 활동 기록은 실제로 한 행동의 축이다.
- 지출은 독립 입력보다 일정·할 일·이벤트·활동에서 파생되는 흐름을 우선한다.
- 사진과 하루기록은 날짜에 반드시 연결하고, 가능하면 활동이나 계획 중 하나에 느슨하게 연결한다.
- 장소는 일정·할 일·이벤트·활동에서 나온 흐름과, 별도 보관함의 저장 장소를 분리한다.
- 사람 데이터는 현재 문자열 기반 연결이 기본이며, `people` 테이블은 별도 정규화의 출발점이다.
- 검색은 원천 데이터를 복제하지 않고, 현재 테이블을 읽어 조립하는 방식으로 유지한다.

## 코드 구조

- `src/app`: Next.js 라우트 진입점
- `src/app/m`: 모바일 중심 화면 라우트
- `src/components`: 인증, 레이아웃, 공통 UI
- `src/features/calendar`: 일정·할 일·이벤트 입력과 캘린더 계산
- `src/features/records`: 전체 기록 조립, 검색용 인덱스, 파생 데이터 계산
- `src/features/data`: Supabase CRUD 계층
- `src/features/screens`: 화면 단위 조합과 세부 패널
- `src/lib`: Supabase 클라이언트와 인증 헬퍼
- `src/types/domain.ts`: 공유 도메인 타입
- `supabase/schema.sql`: DB 스키마, RLS, Storage 정책의 기준

## 현재 화면 조합 방식

- 라우트 파일은 최대한 얇게 유지하고 feature view만 연결한다.
- 데이터 로딩은 `useRecordsDataState` 같은 공통 훅으로 묶는다.
- 화면 내부에서는 스냅샷 단위로 조립하고, 액션은 `mutations`로 넘긴다.
- 모바일 입력은 시트/드로어 패턴을 우선한다.
- 하루 화면은 날짜별 타임라인과 상세 패널을 분리한다.
- 기타 화면은 사람, 가계부, 지도, 갤러리를 탭으로 묶어 조회 중심 흐름을 만든다.

## 검색 기준

현재 검색은 두 층으로 본다.

1. **키워드 검색**
   - `buildRecordSearchItems`로 기록을 하나의 검색 가능한 아이템 목록으로 만든다.
   - 화면 단에서는 문자열 매칭과 날짜 필터만 사용한다.
2. **자연어 검색**
   - 질문 의도, 날짜, 사람, 장소, 금액, 건강, 사진을 해석하는 상위 계층이다.
   - 자세한 설계는 `docs/natural-language-search.md`를 기준 문서로 둔다.

## 자연어 검색 설계 원칙

- 원천 데이터는 기존 테이블을 그대로 사용하고, 별도 대화 기록 테이블을 먼저 만들지 않는다.
- 검색 후보는 먼저 결정론적으로 모은다.
- LLM은 후보를 이해하기 쉬운 형태로 재정렬하거나 요약하는 데만 쓴다.
- 응답은 반드시 근거 기록을 함께 반환한다.
- 근거가 부족하면 추측하지 말고 “찾지 못했다”로 응답한다.
- Gemini 호출은 서버 측 API 경로로 분리한다.

## 현재 리팩터링 기준

- 화면 데이터 로딩은 가능한 한 공통 훅으로 묶는다.
- 대형 화면은 조합 컴포넌트, 패널, 폼, 상세 뷰로 계속 쪼갠다.
- 검색 관련 로직은 UI와 분리해서 `recordsInsights` 같은 모듈에 모은다.
- 자연어 검색은 `질문 해석`, `후보 선택`, `응답 생성`으로 나눈다.
- 스타일은 `life.css`, `calendar.css`에 계속 누적하지 말고 셸/패널 단위로 분리한다.

## 유지보수 기준

- 새 데이터 입력은 먼저 도메인 타입과 Supabase 스키마를 맞춘다.
- 새 조회 화면은 기존 원천 데이터를 재사용하고 중복 테이블을 만들지 않는다.
- 라우트 파일은 얇게 유지하고 실제 로직은 `src/features/*`에 둔다.
- API 파일의 인증 사용자 조회는 `src/lib/authUser.ts`를 쓴다.
- 실사용 저장/삭제 액션은 로딩, 성공, 실패 메시지를 화면에 표시한다.
- 검색 구조를 바꿀 때는 `src/features/records/search/recordsInsights.ts`와 `src/features/screens/search/SearchView.tsx`를 함께 본다.

## 실서비스 전 체크리스트

- `npm run typecheck`, `npm run lint`, `npm run build` 통과
- Supabase SQL 최신본 적용
- `life-media` 스토리지 버킷과 RLS 정책 확인
- `.env.local`에 Supabase, Gemini, Naver 키 설정
- Settings에서 백업 내보내기/가져오기 동작 확인
- 자연어 검색 응답에 근거 링크가 항상 포함되는지 확인
